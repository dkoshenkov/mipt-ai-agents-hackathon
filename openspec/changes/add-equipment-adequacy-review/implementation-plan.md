# План реализации feat/qualification

План подготовлен 14 ноября 2026 года для изменения `add-equipment-adequacy-review`. Основания — [спецификация](specs/equipment-adequacy-review/spec.md), [дизайн](design.md) и [19 задач приёмки](tasks.md). Ниже предложены структура кода и порядок реализации; требования и номера задач OpenSpec сохраняются. Статус — реализовано; результаты приёмки и соответствие тестам зафиксированы в [tasks.md](tasks.md).

Результат изменения: библиотечный сценарий принимает одну редакцию Markdown ТЗ и приложения, возвращает оценку каждого обязательного технического условия, проверяемые основания, открытые вопросы и фактическое покрытие. После обхода один раз вызывается отдельно настроенная более сильная модель. Поздний ответ адресно пересматривает одно требование.

Конвертация DOCX, интерфейс, хранение между обращениями и изменение оригинала остаются ответственностью вызывающего приложения, как предусмотрено дизайном. Проверки внутренней согласованности и ГОСТ подключаются отдельными сценариями.

## Предлагаемое устройство кода

| Место | Ответственность |
| --- | --- |
| `src/qualification/mod.rs` | Публичные операции первичной проверки и продолжения; последовательность стадий; общий контекст запуска. |
| `src/qualification/types.rs` | Материалы, адреса, требования, оценки, вопросы, покрытие и сериализуемый отчёт. |
| `src/qualification/materials.rs` | Версии исходников, индекс блоков, контекст таблиц и проверка цитат; доступ ко всему исходному комплекту. |
| `src/qualification/extract.rs` | Извлечение самостоятельных обязательных условий и проверка области отсылок. |
| `src/qualification/assessment.rs` | Цикл оценки одного требования, выбор следующего шага и остановка без новых оснований. |
| `src/qualification/sources.rs` | Работа с приложениями, чтение HTML/PDF, сверка кандидата по первоисточнику и учёт прямых загрузок. |
| `src/qualification/review.rs` | Единственный финальный проход, проверка замечаний, добавление, объединение, снятие и локальная сверка. |
| `src/qualification/resume.rs` | Проверка сохранённого отчёта и исходного комплекта; обработка позднего ответа. |
| `src/qualification/prompts.rs` | Статические инструкции и контракты ответов отдельных стадий. |
| `src/runtime/search.rs`, существующие `runtime/stage.rs`, `runtime/grok.rs` | Поисковая операция с общими проверками, бюджетом и журналом; сохранение аннотаций ответа. |
| `tests/qualification_*.rs`, `tests/fixtures/qualification/` | Контрактные, транспортные и сквозные проверки; замороженные исходники и ответы. |
| `examples/equipment_adequacy.rs`, `README.md` | Воспроизводимая демонстрация первого запуска и позднего ответа. |

Имена модулей и публичных типов — предложение реализации. Для адресации нужен переиспользуемый контракт блоков, но реализация qualifications не зависит от завершения 63 задач `add-markdown-consistency-review`. Сейчас соответствующего парсера в коде нет.

Предлагаемые публичные операции:

```text
review_equipment_adequacy(input, options, worker, reviewer, sources)
    -> Result<QualificationReport, QualificationInputError>

resume_equipment_adequacy(input, saved_report, answer, options, worker, sources)
    -> ResumeOutcome
```

Обе операции асинхронные. `worker` и `reviewer` — отдельно настраиваемые runtime; все модельные операции одного обращения используют один `ReviewRun`. У операции продолжения нет параметра финального ревьюера. Некорректное продолжение возвращает причину вместе с прежним отчётом до внешних обращений. Ошибки отдельных стадий после принятия входа сохраняются внутри отчёта.

## Порядок реализации

### 0. Согласовать библиотечную основу и подготовить примеры

Библиотечная основа согласована с `main`: перенесены JSON Schema, маршрутизация к отдельному ревьюеру и соответствующие тесты. Перенос выполнен в рабочей копии без merge-коммита; история Git не менялась. Совместимость `Runtime::step`, `review_223` и прежних локальных моделей проверена.

Шесть предупреждений строгой валидации устранены: независимые обязательства разделены на 16 требований. Все 26 исходных сценариев сохранены, добавлен сценарий диапазона и альтернатив. Строгая валидация OpenSpec проходит.

Зафиксировать короткие Markdown-примеры и эталоны из спецификации: весы, память твердомера, радиусные шаблоны, климатическая камера, интерфейсы и затвор камеры. Для исходной и исправленной редакций использовать независимые входы. Методика с 0,02 г, серия из 120 записей и чертёж с R3 — явно заданные тестовые уточнения.

**Готовность:** исходные тесты проходят; для каждого примера определены требование, обязательные цитаты, ожидаемый исход и покрытие. Изменения редактора сами по себе не определяют правильный технический параметр.

### 1. Материалы, адреса и контракт отчёта

Соответствует задачам **1.1–1.2**.

Ввести идентификатор материала, неизменяемую версию, исходную видимость и содержимое. Версию вычислять по исходным байтам, например SHA-256; имя файла не служит версией. Отчёт сохраняет весь первоначальный комплект, включая ещё не цитированные вложения. Для извлечённого представления HTML/PDF сохранять связь с версией оригинала.

Проиндексировать абзацы, списки, заголовки и строки таблиц до вызова извлечения. Для Markdown сохранять диапазоны UTF-8 `[start, end)`; для HTML/PDF дополнительно сохранять раздел или страницу и контекст строки/столбца. Pipe- и HTML-таблицы должны сохранять связь значения с единицей, моделью и оговоркой. Неподдержанная геометрия даёт адресованный пропуск.

Разделить обязательное условие, справочный факт и неустановленную область действия. Для условия из приложения сохранять и отсылку ТЗ, и применимый фрагмент приложения. Найденная характеристика паспорта не становится требованием без основания обязательности.

В отчёте раздельно хранить предметную оценку, недостающий факт/вопрос и техническую остановку. Состояние покрытия блока и финального ревью также хранится отдельно. Подтверждённый открытый вопрос допустим при полном обходе.

**Готовность:** отчёт сериализуется и восстанавливается; повторяющееся «0,1 г» открывает нужную строку; обязательный столбец A отличается от справочного B; неоднозначная отсылка делает покрытие частичным.

### 2. Извлечение и внешний цикл

Соответствует задачам **1.3–1.4**.

Извлекать условия через `Runtime::step<T>` ограниченными пакетами с контекстом. Проверять цитаты, версии, позицию и основание обязательности до добавления записи. Идентификаторы назначает сценарий; порядок определяется исходным документом.

Одно независимое условие получает одну запись: предел весов и шаг — две, диапазон R7–R25 — одна, «GigE Vision или USB3 Vision» — одна с альтернативами. Сохранять оператор, единицу, режимы и оговорки. Блоки с пустым результатом извлечения остаются доступны финальному ревьюеру.

Обходить требования последовательно и сохранять исход каждого. Открытый вопрос не останавливает соседние требования. Ошибка извлечения привязывается к блоку; после исчерпания бюджета оставшиеся известные требования получают техническую причину остановки.

**Готовность:** отчёт различает ноль применимых требований и пропущенную таблицу; три требования могут одновременно иметь оценку, вопрос и технический исход.

### 3. Оценка требования на имеющихся материалах

Соответствует задачам **2.1–2.3** и локальной части **3.2–3.3**.

Ввести типизированный ответ модели: оценка с основаниями либо следующий шаг — прочитать материал, уточнить рабочую задачу или найти технический факт. Код проверяет принадлежность действия текущему требованию и ссылки на фактически прочитанные источники.

Проверять допустимую по ТЗ комплектацию относительно операции, условий и критерия приёмки. Для «недостаточно» нужны допускаемый случай и невыполнимая операция; для «возможно избыточно» — менее строгое условие, покрывающее подтверждённые режимы и запас; для «обосновано» — основание выбранной границы или свойства. Сведения об одной характеристике не обосновывают другую.

Сначала искать ответ в ТЗ, приложениях и полученных уточнениях. Новый подтверждённый факт возвращает на оценку того же требования. Повтор того же факта, включая пересказ, не продлевает цикл. Неизвестный режим работы требует адресного вопроса, а технический сбой сохраняет собственную причину.

Новизну проверять по содержанию факта: модель/редакция, параметр, нормализованное значение и условия. Второй URL с тем же фактом может дополнить происхождение, но сам по себе не даёт новой итерации оценки.

**Готовность:** шаг 0,1 г недостаточен для задачи различать 0,02 г; минимум 1000 записей потенциально избыточен при подтверждённом максимуме 120 с запасом; добавление R3 меняет только оценку диапазона. Приложенный подходящий паспорт используется без поиска и сетевой загрузки.

Это первый рабочий срез для отладки: от Markdown до оценок и вопросов на локальных материалах. До подключения финального ревью соответствующая стадия отмечается незавершённой.

### 4. Поиск и прямое чтение первоисточника

Соответствует задачам **3.1–3.4**.

Добавить отдельную поисковую операцию runtime. Переиспользовать подготовку полей, проверку происхождения, резервирование попытки, тайм-аут и безопасный журнал. Существующий `Model::complete` и текстовый режим сохраняют совместимость. Поисковый контракт возвращает кандидатов, аннотации и статистику; он не объявляет найденное значение подтверждённым фактом.

На записывающем транспорте зафиксировать `POST /v1/responses` с `web_search` и извлечение URL из аннотаций. Проверить случай, когда URL есть только в общем списке: он может служить адресом кандидата, но не доказательством связи конкретного значения с источником. Незавершённый ответ или клиентское действие не принимаются как успешный результат. Внутренние вызовы инструмента учитывать отдельно от одной отправки модели.

Прямо читать HTML/PDF первичного издателя через подменяемый транспорт. Проверять публичность адреса и каждого перенаправления; ограничивать длительность, размер и число фактических HTTP-запросов. Прямые загрузки имеют собственный бюджет. Автоматические повторы и переадресации не должны скрывать расход.

Сверять цитату, модель/редакцию, параметр, значение, режим и заголовки таблицы. Для числовой характеристики проверять применимую единицу; для качественной, например глобального затвора, единица не нужна. Нечитаемый PDF, соседняя модель и отсутствующая цитата оставляют факт неподтверждённым.

**Готовность:** подтверждаются 50 МГц для A и отклоняются 100 МГц из столбца B; HTML и PDF воспроизводятся на снимках; Private/Unknown и исчерпанный бюджет дают ноль отправок на этот шаг; отправленные 429/тайм-аут расходуют попытку и сохраняют прежние результаты.

### 5. Единственное финальное ревью и сверка

Соответствует задачам **4.1–4.4**.

После обхода, включая пустой список требований, передать более сильной модели исходные блоки ТЗ и приложений, отсылки, справочные фрагменты, текущие записи, вопросы и доказательства. Успех ревью — один завершённый вызов; локальный отказ или сбой сохраняет частичный отчёт. Если контекст вмещает только часть материала, явно перечислить пропущенные блоки.

В планировщике по возможности оставлять одну попытку для ревью. Счётчик `ReviewRun` расходуется только при фактической отправке. Дополнительный бюджет внутри сценария не создаётся.

Ревьюер возвращает адресованные замечания и сопоставление исходных условий с записями. Код проверяет идентификаторы, цитаты, обязательность и область действия до применения. Пропуск добавляется; спорная оценка возвращается исполнителю; вопрос сначала проверяется по материалам. Дубли и части одного условия объединяются под первым идентификатором, справочная лишняя запись снимается. История содержит причины, прежние ID и сохранившийся ID; устаревшие вопросы закрываются.

Затем локально проверить соответствие в обе стороны: у каждого обязательного условия одна текущая запись, у каждой записи есть основание обязательности, у каждого замечания есть исход обработки. Эта сверка проверяет адреса и состав записей, а семантическую полноту оценивает модель по оригиналу. Недоказанное объединение или снятие сохраняет записи и частичное покрытие. Второго финального ревью нет; адресная доработка использует исполнителя и остаток общего бюджета.

**Готовность:** восстанавливается пропущенный шаг весов; два интерфейса становятся одной альтернативой; снимается справочный столбец B; соседние ID и оценки сохраняются; финальный ревьюер вызывается не более одного раза.

### 6. Поздний ответ и восстановление отчёта

Соответствует задачам **5.1–5.2**.

До внешнего вызова сверить сохранённый отчёт с ТЗ и всеми первоначальными приложениями: идентификаторы, версии и исходную видимость. Затем проверить открытый вопрос, требование, цитату и запрошенный факт. Недостающий паспорт, подменённая версия, изменённая видимость, закрытый или чужой вопрос возвращают прежний отчёт и причину.

При совпадении создать новый `ReviewRun` и запустить цикл одного требования с ответом и его видимостью. Доступен весь исходный комплект, включая ещё не цитированные страницы. Соседние записи, история и отметка финального ревью сохраняются; новое извлечение и финальное ревью не выполняются.

**Готовность:** после сериализации и загрузки в новом процессе ответ о режиме камеры приводит к нужной строке ранее не цитированной страницы приложенного паспорта. Поисков и прямых загрузок за этим фактом нет; меняется только адресованный результат.

### 7. Демонстрация, регрессия и закрытие изменения

Соответствует задачам **5.3–5.4**.

Добавить `equipment_adequacy` с записанными ответами исполнителя, поиска и ревьюера, снимками HTML/PDF и двумя независимыми Markdown-входами. Показать оценки, источники, вопросы и покрытие до и после позднего ответа. Подготовить точную инструкцию запуска.

Проверки добавляются вместе с соответствующими этапами. Финальная приёмка:

```sh
cargo fmt --all -- --check
cargo test --offline --locked
cargo run --offline --locked --example equipment_adequacy
openspec validate add-equipment-adequacy-review --strict --no-interactive
```

Команды Cargo предполагают заранее подготовленный кеш зависимостей. После согласованного изменения зависимостей сохранить `Cargo.lock` и проверить офлайн-запуск. Локальные подмены подтверждают исполнение и контракты. Предметное качество проверять отдельно на размеченных примерах; при живом прогоне записать модель, настройки, версии материалов, дату, вызовы и расхождения со снимком.

**Готовность:** все 19 пунктов имеют наблюдаемую приёмку, примеры воспроизводимы без ключа, прежние `typed_stage` и `review_223` работают. Флажки `tasks.md` закрываются только после соответствующей реализации и проверки.
