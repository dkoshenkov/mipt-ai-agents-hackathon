# Задачи реализации проверки требований

Порядок реализации, предлагаемые модули, зависимости и соответствие задачам описаны в [плане реализации](implementation-plan.md). Флажки ниже отражают выполненную приёмку.

## 1. Выделение требований и покрытие ТЗ

- [x] 1.1 Описать вход одной редакции, привязку требования к позиции и источнику, предметные исходы, вопрос и техническую остановку. При сериализации и восстановлении отчёта проверить разные исходы двух требований одной позиции и сохранность идентификатора, версии и видимости каждого материала, включая ещё не цитированный паспорт.
- [x] 1.2 Сохранить адресуемые исходные блоки и основание обязательности для позиции. На таблице с моделями A и B проверить отсылку к столбцу A, ноль требований из справочного столбца B и сохранение обоих фрагментов для ревью. Проверить также целиком справочный паспорт и частичное покрытие при неясной отсылке.
- [x] 1.3 Извлечь самостоятельные обязательные условия с привязкой к блокам. На ячейке весов проверить две записи, порядок, правильный адрес повторяющегося «0,1 г» и сохранение «не более». При пустом результате извлечения исходная ячейка остаётся доступна ревьюеру. Диапазон R7–R25 даёт одну запись с двумя границами.
- [x] 1.4 Реализовать внешний цикл и учёт покрытия. Тест с тремя требованиями должен вернуть оценку, открытый вопрос и техническую ошибку по их исходным номерам. Отдельно проверить ноль технических требований, пропущенную таблицу и причину остановки у известных требований, оставшихся после исчерпания бюджета.

## 2. Оценка одного требования и вопросы

- [x] 2.1 Реализовать сопоставление порога с задачей и проверку оснований ответа модели. Проверить «недостаточно» для шага 0,1 г при задаче различать 0,02 г, «возможно избыточно» для 1000 записей при подтверждённом максимуме 120 с запасом и «обосновано» для требуемого диапазона R7–R25. Добавление R3 в чертёж должно менять только вывод по диапазону.
- [x] 2.2 Реализовать выбор между работой с имеющимися материалами, вопросом о задаче и поиском технического факта. На примере камеры проверить использование оговорки о +180 °C, а на примере твердомера — вопрос о максимуме записей до выгрузки. Если паспорт уже передан и подходит, повторных запросов за тем же фактом быть не должно.
- [x] 2.3 Реализовать повторную оценку в пределах текущего требования и завершение при отсутствии новых оснований. На записанных ответах проверить возврат нового факта к тому же номеру, остановку на повторном факте и переход к следующему требованию при открытом вопросе.

## 3. Поиск и прямая сверка первоисточника

- [x] 3.1 Добавить поисковую операцию в текущий runtime с общей подготовкой данных, бюджетом, тайм-аутом и безопасным журналом. На записывающем HTTP-транспорте проверить `POST /v1/responses` с инструментом `web_search`, отсутствие отправки для Private/Unknown и исчерпанного бюджета, расход попытки на каждую отправку, включая повтор после 429, и учёт тайм-аута. Обычный текстовый шаг по-прежнему отправляет запрос без инструмента.
- [x] 3.2 Отделить кандидата Grok от подтверждённого факта. Использовать подходящее вложение до поиска, иначе читать найденный HTML или PDF напрямую. Проверить на локальных снимках успешное чтение обоих форматов, ноль сетевых запросов при наличии паспорта, нечитабельный PDF и недоступную страницу. На записанных ответах xAI проверить URL только в общем списке, незавершённый ответ и клиентское действие.
- [x] 3.3 Сверить параметр, значение, модель или редакцию и применимые условия по цитате с адресом и заголовками таблицы. В числовом примере отклонить выдуманную цитату, 100 МГц из соседнего столбца B и значение без необходимой единицы. Принять подтверждённые 50 МГц для A. В качественном примере подтвердить глобальный затвор по строке паспорта камеры с отсутствующим полем единицы.
- [x] 3.4 Подключить прямое чтение и поиск к внутреннему циклу. Транспортный тест проверяет допустимость адреса до загрузки и при перенаправлении, лимиты чтения, отдельный учёт HTTP и общую границу попыток модели. Убедиться, что текст страницы обрабатывается как данные и при сбое сохраняется результат соседнего требования.

## 4. Финальный проход и адресная обработка замечаний

- [x] 4.1 Подключить отдельно настроенную более сильную модель через типизированный runtime и общий бюджет. Проверить, что после обработки последнего требования ревьюер один раз получает оригинал с приложениями, отсылки, справочные фрагменты, решения и доказательства. При нуле извлечённых требований исходные блоки также поступают на ревью.
- [x] 4.2 Сопоставить условия исходных блоков с решениями, проверить адреса замечаний и обработать только затронутые требования. В тесте исполнитель ссылается на целую ячейку, но пропускает шаг 0,1 г. Ревьюер находит шаг, идентификатор и решение по 2 кг сохраняются. Отдельно проверить оспоренный вывод, ответ из методики и единственный открытый вопрос при отсутствии ответа.
- [x] 4.3 Реализовать объединение и снятие по проверенным замечаниям. Из двух записей для GigE Vision и USB3 Vision получить одно заново оценённое условие с обеими альтернативами под первым идентификатором. Снять ошибочную запись из справочного столбца B. Проверить исходы правок с адресами и прежними идентификаторами, закрытие устаревших вопросов и сохранность соседней записи.
- [x] 4.4 Добавить локальную сверку в обе стороны между обязательными условиями и текущими записями, проверить исход каждого замечания. При неподтверждённом объединении или снятии записи остаются на месте. При непроверенном блоке, невалидной привязке, тайм-ауте или отказе до отправки сохраняются результаты и причина частичного покрытия. Записывающий транспорт должен показать не более одной отправки ревьюеру и ни одной после адресной доработки.

## 5. Возврат к вопросу и сквозной пример

- [x] 5.1 Принимать восстановленный отчёт, ответ с видимостью и исходный комплект материалов. До вызова проверить редакцию, требование, открытый вопрос, версии и видимость ТЗ и вложений. На примере весов меняется только результат шага. При повторном или чужом ответе, отсутствии паспорта, подмене версии под тем же именем или смене Private на Public остаётся прежний отчёт с причиной и нулём внешних вызовов.
- [x] 5.2 Проверить поздний ответ в новом процессе с сохранённым отчётом и исходным паспортом камеры. Ответ о режиме должен привести к ранее не цитированной строке нужной страницы. Проверить ссылку на строку, ноль поисков и прямых загрузок, сохранность остальных решений и отсутствие повторного вызова финального ревьюера.
- [x] 5.3 Добавить локальный пример и короткую инструкцию запуска. Проверить команду `cargo run --offline --example equipment_adequacy` на двух независимых Markdown-выдержках. Использовать записанные ответы исполнителя, поиска и ревьюера, а также отдельный снимок первоисточника. Вывести результаты до и после ответа заказчика.
- [x] 5.4 Запустить `cargo test --offline` и сопоставить сквозной отчёт с размеченными ожиданиями по каждой позиции, первичному фрагменту, вопросу и покрытию. Проверить прежние сценарии типизированного runtime и `review_223`.

## Подтверждение приёмки

Реализация проверена 14 ноября 2026 года. Все 60 тестов `cargo test --offline --locked` прошли, включая прежние сценарии библиотеки и пять регрессионных проверок после ревью. Они проверяют ограниченные пакеты, отсылку к приложению из другого пакета, откат правок при невалидной сверке, принадлежность единицы измерения и сохранение вопроса после сбоя переоценки. `cargo clippy --offline --locked --all-targets -- -D warnings`, проверка форматирования и строгая валидация изменения OpenSpec проходят. Два запуска локального примера дают одинаковый JSON. Живые вызовы xAI и оценка качества настоящей модели в эту приёмку не входят.
