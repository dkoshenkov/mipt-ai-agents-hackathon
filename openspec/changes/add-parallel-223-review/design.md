# Design

## Context

Вход ветки по 223-ФЗ — Markdown. Вызывающая сторона передает документ со статусом открытости данных, список включенных проверок и настройки моделей. Список может меняться между запусками.

## Goals / Non-Goals

Участник команды подключает проверку через список и пишет последовательность стадий как обычную `async fn`. При необходимости в эту функцию можно добавить `if`, `for` или `match`. Другие ветки и общая сводка по документу получат собственные сценарии. Предметные промпты, разбор DOCX и межсессионная память остаются отдельными задачами.

## Decisions

| Модуль одного библиотечного crate | Ответственность |
| --- | --- |
| `core` | Документ и его фрагменты, находки с цитатами и ссылками на исходник, исходы проверок, агрегация и тип результата ветки. Агрегацию можно вызвать синхронно на тестовых данных. |
| `runtime` | Вызовы Grok через Rig, конкурентный запуск через Tokio и futures, проверка допустимости внешнего запроса, тайм-ауты, вызов критика и структурированный журнал. |

**Конкурентный запуск.** Исполнитель принимает срез проверок. Для каждой проверки он создает future, возвращающую ее ID и результат, затем дожидается всего списка через `futures::future::join_all`. Поэтому быстрая ошибка 429 и более поздняя находка обе попадут в агрегат в порядке входного списка. Каждая попытка ограничена тайм-аутом. Число одновременных запросов не входит в публичную сигнатуру. [Семантика join_all](https://docs.rs/futures/latest/futures/future/fn.join_all.html) · [Квоты xAI](https://docs.x.ai/developers/rate-limits)

**Агрегация.** Запись успешной проверки содержит ее находки, включая случай пустого списка. Запись сбоя содержит ошибку с ID проверки. Агрегатор связывает цитаты с фрагментами исходного Markdown. Текст документа и агрегированные исходы доступны критику. Полнота проверки вычисляется по исходам агентов независимо от заключения критика.

**Критик и передача данных.** Для допустимого входа критик вызывается один раз после завершения всех проверок, в том числе если каждая завершилась ошибкой. Адаптер выполняет одну попытку обращения к модели, включая случай невалидного ответа. До первого внешнего запроса проверяются документ и заранее известные материалы. Если автор добавил контекст позже, его открытость проверяется перед отправкой критику. Отказ на этой стадии возвращается вместе с собранными находками.

**Журнал.** Для запуска по умолчанию включен `tracing`. События начала и завершения стадий содержат общий `run_id`, этап, ID проверки или имя модели по применимости. Событие завершения содержит длительность и исход. Для сбоев пишется категория ошибки. Документ, цитаты, промпты, ответы провайдера и ключи исключены из журнала.

### Пример для команды

Эскиз публичного API. Аргументы функции показывают, что меняет автор ветки. Ошибки исходных параметров приходят до запуска проверок. После агрегации отчет владеет находками в обеих ветках `match`.

```rust
async fn review_223(
    runtime: &Runtime,
    document: &Document,
    checks: &[Check],
) -> Result<BranchReport, InputError> {
    let outcomes = runtime.run_parallel(document, checks).await?;
    let evidence = aggregate(document, outcomes);

    let report = match runtime.review(document, &evidence).await {
        Ok(verdict) => BranchReport::Reviewed { evidence, verdict },
        Err(error) => BranchReport::CriticFailed { evidence, error },
    };

    Ok(report)
}
```

`Reviewed` означает, что критик вернул заключение. Внутри этого варианта тоже могут быть пропущенные из-за сбоя проверки. `CriticFailed` содержит кандидаты и исходы в том виде, в каком их собрала ветка. Вызывающий код может показать их сотруднику вместе с причиной отсутствия заключения.

В примере на синтетическом Markdown таблица указывает пассажирский лифт, а описание — грузовой. Одна проверка быстро получает HTTP 429, другая позже возвращает расхождение со ссылками на оба фрагмента. При успехе критика отчет содержит его заключение, обе ссылки и сведения о сбое проверки. При тайм-ауте критика тот же агрегат доступен в `CriticFailed`. Для демонстрации обоих исходов достаточно локально заданных ответов.

## Risks / Trade-offs

- Полный документ и результаты проверок могут превысить контекст модели. В первом драфте такая ошибка возвращается в отчете. Компактный вход из подтвержденных цитат и заголовков можно сравнить с полным документом отдельно. [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)
- Публичные операции дают команде возможность управлять ходом сценария и видеть входные данные каждого вызова. Этот же контракт используется в локальном примере с подменой ответов. [HumanLayer, 12 Factor Agents](https://www.humanlayer.dev/blog/12-factor-agents)
- Для повторного применения вывода между документами потребуется хранить его происхождение и область применимости. Решение о памяти можно принять отдельно от API запуска проверок. [Anthropic, The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)
