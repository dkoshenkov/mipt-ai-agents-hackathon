# Design

## Context

`Runtime::request_json<T>` уже ставит тайм-аут, вызывает `Model::complete` и десериализует JSON. Он доступен внутри crate и принимает готовую строку. В действующем сценарии 223-ФЗ исходный документ и дополнительные документы проверяют до отправки, общедоступный `Evidence` не несёт происхождения отдельных значений. `Grok::complete` извлекает только текст ответа. Инициализация журнала и идентификатор запуска сейчас находятся в `review_223`.

## Goals / Non-Goals

Предлагаемый API обслуживает авторов сценариев, в том числе из другого crate. Он исполняет одну типизированную операцию. Прикладная ветка владеет результатом, проверяет его смысл и решает, что читать следующим. Локальная подмена воспроизводит интерфейс модели без внешних запросов.

## Decisions

1. Предоставить на `Runtime` типизированную операцию и небольшой общий контекст запуска с идентификатором и бюджетом. Существующий `request_json<T>` остаётся внутренней деталью. Проверить доступность новой операции со стороны интеграционного теста через публичные экспорты crate. Вход содержит фиксированную инструкцию приложения, контролируемую метку стадии и сериализуемые данные с происхождением. Из проверенного набора сам runtime собирает отправляемый prompt. Пара «произвольная готовая строка и отдельно список открытых документов» позволила бы отправить данные, отсутствующие в этом списке.
2. Статус задаёт приложение при получении исходника. Производное значение ссылается на источники, участвовавшие в его вычислении. Частный или неизвестный источник ограничивает передачу всего значения. Успех первого вызова не даёт разрешения на новые материалы. Это контракт между библиотекой и вызывающим кодом, который знает происхождение данных. Содержимое текста само по себе не устанавливает его открытость.
3. После проверки данных и подготовки сообщения атомарно получить последнюю доступную попытку. Граница учёта — передача вызова адаптеру модели, наблюдаемая тестовым транспортом. Тайм-аут после передачи сохраняет расход, даже если доставка на сервер неизвестна. До передачи расход равен нулю. Локальный отказ по бюджету различим от HTTP 429. Использовать отдельный исход нового шага для локальных отказов и существующие категории ошибок модели, чтобы избежать несовместимого расширения публичного enum для старых клиентов.
4. Сохранить существующее транспортное API и однократную отправку. В Grok исследовать полный структурированный ответ до `.text()`: наличие запроса функции даёт `InvalidResponse`, даже если в сообщении есть JSON. Проверить также причину остановки в структурированном ответе Rig 0.46.0. Остановка по лимиту с корректным JSON (например, пустым массивом) возвращает ошибку. До десериализации проверять также элементы ответа, требующие продолжения на стороне клиента. В локальной пробе RecordingHttpClient с диалектом xAI элемент mcp_approval_request рядом с текстом [] дал stop=Stop и ноль элементов tool_calls(). Поэтому проверка использует вид исходного элемента либо его сохранённое представление в сообщении. Служебные элементы, которые не требуют действия, сами по себе не делают нормальный текстовый ответ ошибочным. Проверять форму через serde, а ссылки, ID и допустимость значений контролирует вызывающая стадия. Успешное событие этой операции означает «ответ декодирован»; предметное решение записывается отдельным событием сценария.
5. Использовать имеющийся `tracing`, добавив возможность открыть запуск для нового вызывающего кода и получить его итоговое число попыток. Разрешены внутренний ID запуска, контролируемый код стадии, номер попытки при отправке, длительность и категория исхода. Входные ID, свободное имя модели и текст ошибки могут содержать данные заказчика. Проверка журнала должна передавать контрольные строки непосредственно в эти поля.

## Risks / Trade-offs

- Обобщение старой `review` на произвольный агрегат с неизвестным происхождением позволило бы обойти новый контракт. Новая ветка вызывает защищённую операцию для каждого внешнего шага. Гарантия для произвольного чужого `Evidence` через старый публичный API требует отдельного разбора совместимости.
- Однократное резервирование общего лимита допускает разный порядок конкурирующих стадий. Тест фиксирует число допущенных отправок и исходы, сохраняя свободу планировщика.
- Предметный протокол «решение или дочитывание», сохранение доказательств, отчёт о покрытии и проверка правок принадлежат [сценарию Markdown](../add-markdown-consistency-review/design.md). Эти задачи проверяются на его данных.

## Устройство операции для согласования

Предлагаемый вызов со стороны отдельного crate выглядит как `runtime.step::<Claims>(&run, &stage_request).await`. Входные типы и результат экспортируются из `runtime`. Сигнатура служит эскизом API. Один экземпляр контекста живёт на весь запуск, включая повторный анализ рабочей копии. При позднем ответе пользователя сценарий создаёт новый контекст.

| Где реализовать | Ответственность | Граница проверки |
| --- | --- | --- |
| `src/runtime.rs`, новый небольшой модуль `runtime/stage.rs` | `ReviewRun` хранит внутренний ID, предел и атомарный счётчик. `StageRequest` содержит контролируемую метку стадии, статическую инструкцию приложения и список сериализуемых полей с источниками. | Внешний интеграционный тест создаёт запрос без доступа к полям Runtime. Для производного поля передаются все источники, из которых получено значение. Пустое множество источников для данных отклоняется. |
| Операция `step<T>` | Проверить происхождение, сериализовать одобренные поля, атомарно занять попытку, сразу передать вызов существующему `request_json<T>`. Счётчик является общим для переданных ссылок на запуск. | Внутри операции сериализация поля возвращает Result. Ошибку подготовки вернуть до занятия попытки, в журнал передать только контролируемую категорию. Между занятием попытки и передачей в адаптер нет ожидания. Локальный отказ сохраняет счётчик. Прерванная после передачи попытка учитывается один раз. |
| `runtime/grok.rs` | До извлечения текста проверить завершение и элементы структурированного ответа. Обработать нативный вызов и непрозрачный элемент действия из воспроизведённого случая. | Два записанных HTTP-ответа с тем же текстом `[]` и разным структурированным исходом получают разные результаты. |
| `runtime/logging.rs` | События начала, отправки и исхода содержат внутренний ID, код стадии, номер занятой попытки, категорию, длительность. | Счётчик отправок в журнале совпадает с подменой модели. Локальный отказ не получает номера новой попытки. |

Тип результата выражает успешное декодирование либо отказ (происхождение, локальный лимит, ошибка подготовки или категория ошибки модели). Состояние предыдущих шагов хранит потребитель. Публичный Model продолжает принимать текст и выполнять одну попытку. Для тестов достаточно существующих подмен Model и RecordingHttpClient. Внутренняя операция чтения блока и адаптер каталога принадлежат прикладному изменению. В [плане библиотеки](tasks.md) есть отдельная приёмка для каждого из этих контрактов.
