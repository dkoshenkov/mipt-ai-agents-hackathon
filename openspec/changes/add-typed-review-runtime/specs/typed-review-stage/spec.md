# Контракт типизированного вызова

## Purpose

Библиотека даёт автору сценария один контролируемый вызов модели, возвращает типизированный исход и сообщает, была ли израсходована попытка из бюджета текущего запуска.

## ADDED Requirements

### Requirement: Контекст запроса
Операция SHALL строить внешнее сообщение из инструкций приложения и данных с известным происхождением. Перед каждой отправкой все отправляемые данные, включая производные значения и поздние добавления, SHALL иметь подтверждённый статус Public по всем исходным материалам. Запись запрета SHALL предшествовать обращению к модели и не расходовать попытку.

#### Scenario: Производные данные из нескольких источников
- **WHEN** в сводке использованы открытый документ и уточнение со статусом Private либо Unknown
- **THEN** возвращается отказ по контексту, в тестовом транспорте ноль вызовов и число доступных попыток прежнее. Публичная метка открытого документа не распространяется на сводку.

#### Scenario: Новый материал на втором шаге
- **WHEN** первый шаг прошёл успешно, а для следующего сценарий передал значение без установленного происхождения
- **THEN** второй вызов отклонён до отправки. Вызывающая сторона по-прежнему владеет результатом первого.

### Requirement: Попытки и типизированный результат
Операция SHALL принимать ожидаемый тип результата, после некорректного ответа выполнять до трёх повторных отправок в пределах бюджета запуска и возвращать значение или различимую причину отказа. В текстовом режиме результатом считается завершённый текстовый ответ допустимой формы. Нативное действие провайдера, требующее продолжения, SHALL завершаться ошибкой формы до использования текста.

#### Scenario: Ответ ожидаемой формы
- **WHEN** модель возвращает корректный JSON согласованного типа
- **THEN** вызывающая сторона получает десериализованное значение за одну попытку и может выполнить предметную проверку полей.

#### Scenario: Значение не сериализуется до отправки
- **WHEN** публичный вызов получает разрешённое поле, для которого сериализация возвращает ошибку, а затем корректное поле при исходном лимите в одну попытку
- **THEN** первый запрос возвращает локальную ошибку подготовки без паники, вызовов модели и расхода попытки. Второй запрос в том же запуске успешно декодируется, модель видит всего один вызов.

#### Scenario: Ошибка после отправки
- **WHEN** модель возвращает пустой ответ, неверный JSON, неподходящую форму, HTTP 429, ошибку провайдера либо превышает тайм-аут
- **THEN** вызывающая сторона различает ошибку формы, ограничение частоты, ошибку провайдера и тайм-аут. Каждая отправка расходует одну попытку. При ошибке формы допускаются до трёх повторных отправок. При HTTP 429, 500, 502, 503 или 504 допускаются до двух дополнительных отправок с возрастающей паузой и учётом Retry-After в пределах бюджета и настроенного тайм-аута. Если запрошенная задержка не помещается в допустимое ожидание, вызов завершается без раннего повтора. Тайм-аут и прочие сбои провайдера завершают вызов.

#### Scenario: Ответ с вызовом функции
- **WHEN** транспорт получил нативный вызов функции отдельно или вместе с корректным текстовым JSON
- **THEN** ответ отклоняется до использования текста. Вызов функции не исполняется. Пока доступен бюджет, разрешён повтор исходного типизированного запроса.

#### Scenario: Завершённый HTTP-ответ содержит запрос подтверждения
- **WHEN** один ответ содержит статус completed, текст `[]` и элемент `mcp_approval_request`
- **THEN** текстовый вызов возвращает InvalidResponse при бюджете в одну попытку. Запрос подтверждения не исполняется и результат не используется как пустой список. Для ответа с тем же статусом и только текстом `[]` десериализация списка успешна.

#### Scenario: Незавершённый ответ с корректным JSON
- **WHEN** при исчерпании лимита токенов провайдер вернул статус incomplete и текст `[]`, который подходит по типу
- **THEN** при сохранении ошибки до исчерпания повторов операция возвращает ошибку ответа. Результат не может означать «проблем не найдено».

### Requirement: Общий бюджет и журнал
Операция SHALL расходовать одну попытку непосредственно при передаче проверенного запроса модели. Параллельные стадии одного запуска SHALL делить бюджет, разные запуски SHALL иметь независимые бюджеты. Исчерпание возвращается отдельно от ошибки модели. По журналу SHALL быть различимы запуск, стадия, обращение к модели, длительность и исход. Журнал содержит только контролируемые приложением метки и счётчики.

#### Scenario: Конкуренция и нулевой бюджет
- **WHEN** две готовые стадии одного запуска претендуют на последнюю попытку
- **THEN** тестовая модель видит один вызов, другая стадия получает отказ по бюджету. При изначально нулевом бюджете вызовов нет, а отдельный запуск со своим лимитом выполняется независимо.

#### Scenario: Учёт позднего сбоя и локального отказа
- **WHEN** первая отправка закончилась тайм-аутом, а следующий запрос остановлен до отправки
- **THEN** счётчик фактических попыток равен одному. Журнал различает оба исхода и не содержит исходные данные, промпты, ответы, произвольные идентификаторы из документа, тексты исключений и секреты.

### Requirement: Совместимость библиотеки
Существующие вызовы проверок по 223-ФЗ SHALL сохранять исходный API, порядок результатов, число попыток и обработку поддерживаемых успешных и частично успешных ответов.

#### Scenario: Старый сценарий
- **WHEN** одна существующая проверка успешна, другая получила 429, а критик завершился по тайм-ауту
- **THEN** возвращаются прежние результаты с привязками, ошибка соседа и ошибка критика, выполнена одна попытка на каждую проверку и одна на критика.
