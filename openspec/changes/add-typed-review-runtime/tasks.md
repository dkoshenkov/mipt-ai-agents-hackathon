# План библиотеки

Эти задачи принадлежат crate procurement-review. [Предметный сценарий](../add-markdown-consistency-review/tasks.md) использует публичный вызов и владеет выбором значений, вопросами и перепроверкой ТЗ.

## 1. Эпик — публичный вызов и происхождение входа

- [ ] 1.1 Открыть внешний типизированный вызов поверх существующего Runtime. Интеграционный тест импортирует API из crate и получает ожидаемую структуру через локальную модель.
- [ ] 1.2 Собирать сообщение внутри операции из фиксированной инструкции и полей с происхождением. Записывающая модель видит только разрешённые поля, пользовательский текст приходит как данные.
- [ ] 1.3 Проверять полный набор источников каждого поля перед отправкой. Производная сводка с Private/Unknown и значение без источника дают ноль отправок и сохраняют бюджет.
- [ ] 1.4 Применять проверку заново при следующем шаге. При закрытом позднем уточнении второй запрос отклоняется, первый типизированный результат остаётся у вызывающего кода.

- [ ] 1.5 Вернуть локальную ошибку подготовки при отказе Serialize. Интеграционный тест через публичный API подаёт поле, для которого сериализация возвращает ошибку, и затем корректное поле при лимите в одну попытку. Проверить отсутствие паники, ноль вызовов для первого поля и один успешный для второго.

## 2. Эпик — бюджет запуска и причины остановки

- [ ] 2.1 Реализовать общий для стадий счётчик попыток запуска. В гонке за последний слот модель вызывается один раз, при нулевом лимите ни разу, в новом запуске действует собственный лимит.
- [ ] 2.2 Различать отказ до отправки и ошибку одной переданной попытки. На 429, тайм-ауте, ошибке провайдера и JSON неверной схемы сверить категорию и одну попытку без повтора. Исчерпанный локальный лимит даёт отдельную причину.
- [ ] 2.3 Привязать ограниченный набор событий tracing к запуску и стадии. Сверить журнал двух одновременных запусков с вызовами модели. Событие декодирования отличается от отказа до отправки.
- [ ] 2.4 Проверить отсутствие чувствительных значений в журнале. Контрольные строки из документа, имени модели, внешнего ID, промпта, ответа и ошибки отсутствуют в записанных событиях.

## 3. Эпик — текстовый ответ Grok

Может выполняться параллельно эпику 1. Приёмка использует RecordingHttpClient и диалект xAI из зафиксированной версии Rig.

- [ ] 3.1 Проверять завершённость ответа до чтения текста. Чистый completed с массивом проходит, incomplete по лимиту даже с валидным JSON возвращает InvalidResponse.
- [ ] 3.2 Отклонять нативное действие провайдера в текстовом вызове. Для tool-only и text + tool проверить InvalidResponse и ровно один запрос транспорта.
- [ ] 3.3 Распознать требование клиентского подтверждения в непрозрачном элементе. Отличить completed с текстом [] и mcp_approval_request от нормального completed с тем же текстом. Приёмка проверяет также обычный служебный элемент без действия.

## 4. Эпик — совместимость и пример потребителя

- [ ] 4.1 Проверить контракт существующего review_223. В cargo test --locked сверить частичный успех, порядок, исход критика по тайм-ауту, цитаты и число обращений.
- [ ] 4.2 Документировать вызов в README на исполняемом локальном примере. Потребитель декодирует ответ через публичный API, самостоятельно отклоняет неверный предметный ID и сохраняет предыдущее доказательство.
